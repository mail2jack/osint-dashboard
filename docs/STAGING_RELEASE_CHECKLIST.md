# Joost — staging release checklist

**Scope:** local or isolated staging only  
**Production:** this checklist does not authorize deployment or database changes

## 1. Safety boundary

- [ ] Confirm the branch and commit under review.
- [ ] Confirm production credentials, domains and external provider secrets are
      not loaded in staging.
- [ ] Confirm all external integrations use mocks or dedicated test accounts.
- [ ] Confirm the production VPS has not been changed.
- [ ] Record the intended rollback point before any staging deployment.

## 2. Application and database

- [ ] Start PostgreSQL, Redis and application services in the isolated staging
      environment.
- [ ] Confirm health checks and application logs are clean.
- [ ] Run migrations only against the staging database.
- [ ] Run `alembic check` against staging and investigate every reported drift;
      do not apply a bulk autogenerated migration.
- [ ] Verify tenant isolation with at least two synthetic tenants.
- [ ] Verify tenant purge in dry-run mode before any destructive test.
- [ ] Verify background tasks restore their persisted tenant context.

## 3. Security and privacy

- [ ] Confirm non-admin users cannot access settings or platform controls.
- [ ] Confirm cross-tenant reads and writes are rejected or return no data.
- [ ] Confirm API keys require an active user in the same tenant.
- [ ] Confirm encrypted settings are encrypted at rest and masked in HTML, API
      responses and audit logs.
- [ ] Confirm webhook destinations are public HTTPS only and contain no
      embedded credentials.
- [ ] Confirm secrets do not occur in logs, reports, webhook bodies or test
      artifacts.

## 4. Functional regression

- [ ] Run the full test suite with the required test environment variables.
- [ ] Run Ruff and mypy using the same commands as CI.
- [ ] Test case, subject, research-action, candidate/result, finding,
      validation and report flows with synthetic data.
- [ ] Test JSON, CSV and PDF exports for tenant isolation.
- [ ] Test audit trail entries for important mutations without secret values.
- [ ] Record known sandbox-only failures separately from application failures.

## 5. Go/no-go review

- [ ] Review the report-inclusion policy for verified versus explicitly
      reportable findings.
- [ ] Confirm the approved telemetry fields, replacement-based retention and
      provider-side/legal evidence.
- [ ] Confirm each external provider is approved for the specific data
      category it receives.
- [ ] Confirm WhatsApp remains disabled in production unless explicitly
      activated, with per-tenant accounts and manual sending only.
- [ ] Review Alembic drift against production evidence, not only local models.
- [ ] Obtain explicit production approval for migration, deployment, restart,
      purge, backup or provider-setting changes.

## Rollback rule

Stop immediately when a tenant-isolation check fails, a secret appears in an
unapproved output, a migration differs unexpectedly, or a production resource
is detected. Preserve logs and the staging database for investigation. Do not
continue toward production until the finding is understood and explicitly
approved.
