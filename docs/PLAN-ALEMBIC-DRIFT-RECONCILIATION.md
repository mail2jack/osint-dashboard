# Alembic model/schema drift — reconciliation plan

**Status:** analysis only; no migration generated or applied  
**Environment checked:** local Docker PostgreSQL staging  
**Checked:** 2026-09-26

The repository's standalone development fallback database (`cms.db`) is a
separate state: a read-only check showed no recorded Alembic revision there.
That explains why running `python -m alembic check` without the Docker
`DATABASE_URL` reports that the target database is not up to date. It must not
be stamped or migrated implicitly; the database choice should be explicit
when validating a release.

## Finding

`alembic check` reaches the current migration head, but reports additional
autogenerate operations. This means the database can be at the latest known
migration while still differing from the current SQLAlchemy model metadata.
It does not, by itself, prove that production has the same differences.

## Classification

### A. Likely historical index drift — verify before changing

The check reports removed or added indexes on cases, clients, subjects,
research actions, invoices, notifications, reminders, findings and several
newer relationship columns. Some of these indexes were deliberately created
and later removed by migrations, while current models or PostgreSQL inspection
may describe them differently. The safe action is to compare actual query
patterns and production index usage before adding or dropping anything.

The local PostgreSQL inspection confirms that several indexes reported by
Alembic as removable are actually present, including:

- `cases`: status, priority, updated-at and tenant/deletion indexes;
- `clients` and `subjects`: tenant/deletion and tenant/name indexes;
- `research_actions`: status, action type and the active photo-analysis
  uniqueness index;
- `invoices`: status and client/status indexes;
- `findings`: the content-hash index;
- `finding_capture_jobs`: both active-job uniqueness indexes.

This is evidence that the model metadata and historical database schema are
out of alignment, not evidence that these indexes are unused. No index should
be dropped based on the current `alembic check` output alone.

### B. Intended schema evolution — reconcile explicitly

- `findings.source_url` is currently 500 characters in PostgreSQL.
- `finding_screenshots.source_url` is currently 2000 characters, deliberately
  expanded by migration `f3a4b5c6d9e0`.
- `clients.deleted_at` exists in the historical schema but is not represented
  consistently in current model metadata.
- The composite `users(id, tenant_id)` uniqueness needed for the API-key
  foreign key is present in the new local migration, but autogenerate reports
  it as a difference because this check predates the migration’s intended
  production rollout state.

The local database inspection confirms that `uq_users_id_tenant_id` is present.

These items need a decision about the desired canonical schema, not a blind
autogenerated migration.

The model declarations were corrected locally to match these database lengths,
and `Client.deleted_at` was added to the model because it already exists in the
schema and is used by `Client.soft_delete()`.

### C. Nullability/default differences — data-risk review required

The check reports differences for breach records, DPA records, invitations,
invoice fields, payments, subject relations and case-subject status. Changing
nullability can fail on existing rows or silently change application behavior.
Each field needs a data-count check, an explicit backfill/default policy and a
separate migration if the stricter rule is intended.

The local database inspection shows that these columns are currently `NOT NULL`
and have defaults, even though the current model declarations do not always
state `nullable=False` explicitly. The safe interpretation is therefore that
the database has a stricter contract than the model metadata. Loosening the
database would be a backwards-incompatible data-governance decision; the first
preferred option is to align the model declarations with the existing database
contract and add regression checks.

### D. Metadata cycle warning — architecture/documentation issue

Alembic warns that `tenants` and `users` have mutually dependent foreign keys.
This affects automatic table ordering and can become an error in a future
Alembic/SQLAlchemy version. It should be handled deliberately in migration
configuration or by simplifying the relationship, not during an unrelated
security fix.

Local PostgreSQL confirms the exact cycle:

- `tenants.owner_id` references `users.id`;
- `users.tenant_id` references `tenants.id`.

This is primarily a schema-lifecycle and maintainability risk. It can require
two-step creation/update logic and careful downgrade ordering. It is not, by
itself, evidence of a tenant-isolation failure.

## Safe next steps

1. Capture production schema metadata only after explicit approval; do not
   assume local staging represents production.
2. Compare each reported index with actual PostgreSQL indexes and usage.
3. Decide canonical lengths and nullability for each affected column.
4. Decide whether `clients.deleted_at` is retired, restored to the model, or
   preserved for compatibility.
5. Re-run `alembic check` after each small, reviewed migration group.
6. Keep the API-key tenant constraint rollout separate from unrelated drift.

## Explicitly not done

- No autogenerated migration was created.
- No production schema was inspected.
- No indexes, columns, constraints or defaults were changed.

## Test note

The non-migration integrity, finding-capture and findings-register tests pass
after the metadata correction. The full historical migration-cycle suite still
has separate failures because the new API-key constraint migration is not
SQLite-downgrade compatible and older tests still expect the previous
migration head. This is tracked separately from the field-length correction.
