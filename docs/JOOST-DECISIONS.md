# Joost — decision register

This document is the durable working record of decisions made during the
technical audit and local hardening work. It is not a production change order.

## Confirmed decisions

1. **Tenant model:** Joost is designed per tenant. Data, users, API keys,
   integrations, exports and background work must remain tenant-scoped.
2. **Integration ownership:** webhook and Twilio configuration belongs to the
   tenant, not to the installation as a whole.
3. **Webhook destinations:** only public HTTPS destinations are allowed.
   Embedded credentials, localhost, loopback, private and link-local IP
   literals are rejected.
4. **Secrets:** secrets are encrypted at rest, masked in the UI/API/audit
   trail, and never copied automatically from legacy global settings.
5. **Auditability:** important tenant-setting changes are recorded with the
   tenant and actor; secret values are never written to the audit record.
6. **Production boundary:** local analysis and staging work must not change
   production without a separate explicit approval.
7. **Migration safety:** Alembic drift is reconciled in small reviewed groups;
   no bulk autogenerated migration is applied automatically.
8. **Communication:** technical explanations should state what something is,
   why it matters, the practical consequence and the recommended action.

## Current implementation status

- API-key user/tenant integrity is protected in application code and locally
  by a PostgreSQL composite foreign key migration.
- Tenant purge, export filtering, background tenant context, webhook/Twilio
  isolation and settings authorization have local regression coverage.
- Local staging uses synthetic data and does not authorize production rollout.

## Open owner decisions

- **Report policy — decided:** only verified findings may appear in official
  reports.
- **Telemetry retention — decided:** all currently collected telemetry is
  allowed, and values may be retained until newer values replace them.
- **External providers — provisional decision:** public technical data is
  allowed; business identifiers require configured provider approval; sensitive
  personal data such as private phone numbers, faces and private addresses
  requires explicit provider approval.
- **WhatsApp — provisional decision:** keep it disabled for production until
  explicitly activated; use a separate account per tenant; begin with manual
  sending; log sender and message action; do not automatically place research
  data in messages.
- Whether DNS-level controls are required in addition to application-level
  webhook destination checks.

## Approval rule

An open decision must not be silently inferred from implementation convenience.
When it affects privacy, external data sharing, production data, migration,
retention or customer-visible behavior, pause and ask the owner.

The external-provider and WhatsApp decisions above are owner-approved defaults
for now and may be revised when operational or legal requirements become
clearer.
